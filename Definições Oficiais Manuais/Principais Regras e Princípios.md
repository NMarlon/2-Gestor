## Princípios e regras de aplicação:
1. Preciso de dinheiro pra me sustentar
2. Todos os projetos que puderem, têm que se transformar em uma forma comercializável, ou um app, ou um site, etc.
3. DEVE ser algo simples e intuitivo, pra que qualquer pessoa, até uma criança consiga entender e usar a proposta (ou projeto que será desenvolvido) com facilidade
4. Deve ser profissional e atrativo
5. DEVE ter um plano de negócio, desde o consumo aproximado de tokens para a criação, público alvo, plataforma usada, valor mínimo de investimento, como está o mercado, como estará o mercado no futuro, prospecção de análise de aderência, planejamento de desenvolvimento, tecnologias que serão usadas, até a satisfação do consumidor final 
6. Deve-se sempre prezar pela qualidade, praticidade, facilidade, simplicidade, o melhor desempenho, confiável e seguro, testado contra os possíveis principais bugs
7. TUDO deve estar documentado, e essa documentação organizada, para ser um mapa para que qualquer IA que vá desenvolver, possa saber o que ler para encontrar, possivelmente, SEM precisar ler TODA a documentação (enconomizando tokens)
8. DEVE se ter prioridade para os projetos de maior rentabilidade e maiores chances de sucesso
9. SEMPRE ao fazer um plano, pesquise bem na internet para desenvolver com os melhores métodos em cada espectro.
10. Procure também ter novas boas ideias para implementar os projetos, para fazê-lo progredir nos nossos propósitos e ser algo ainda mais bom. Registre e documente essas ideias num arquivo específico pra isso.
	1. Se TODAS as tarefas e bugs etc tiverem sido terminados e resolvidos, essas ideias são a próxima coisa para analisar, pesquisar, pedir aprovação (minha, do dev), e então aprovado, seguir os procedimentos para executar.  
11.  Registre os princípios e direcionamento, e boas práticas, esses registros devem ser ter princípios vivos, que mantenham o projeto ativo e se adaptando à realidade, se auto-aperfeiçoando, por essas experiências




### Das boas práticas das IAs
1. Pesquise na internet regularmente sobre os problemas, e sobre melhores práticas, assim economizando tokens e ainda desenvolvendo melhor
2. Por isso também DEVE-SE ter SEMPRE registrado TODO erro e seus aprendizados de cada erro, para que assim, as próximas IAs NÃO caiam no mesmo erro.
3. Mantenha as DOCS ATUALIZADAS
4. O GESTOR pode ler as docs do projeto da raiz do respectivo projeto

## Do GESTOR
---
### Da Organização
1. De PREFERÊNCIA, as DOCS dos projetos devem estar na respectiva pasta do projeto.
	1. PORÉM, se é algo exclusivo e específico do GESTOR com um específico projeto, deve ter uma pasta dentro de DOCS para isso, com uma pasta pra cada projeto que tenhas as docs com informações específicas para o GESTOR que vai começar naquele projeto
	2. A leitura das DOCS do respectivo projeto é opcional, portanto, entenda, que se houver informações exclusivas que é fundamental saber pelo GESTOR (para caso outro GESTOR novo de IA venha à assumir) DEVE conter pelo menos uma linha apontando para as DOCS do projeto e mandando ler o que é fundamental de ser lido (também pra evitar redundância de informação, entre GESTOR e PROJETO)
2. É DEVER ler as respectivas docs do GESTOR <-> PROJETO (da pasta das docs do Gestor)
3. Se encontrar contradição nas docs, adicione no fluxo de tarefas ela deve ser corrigida e atualizada, o aprendizado ou progresso deve relatado num arquivo de histórico do projeto
4. Cada problema ou surpresa que encontrar, verifique o grau de urgência e prioridade, ajuste a lista de tarefas desenvolvendo um bom plano para que tudo se desenvolva de forma organizada, e economizando tokens (por isso também os registros e estarem bem organizados).
5. Lembre-se que MAIS de uma IA GESTOR vai estar trabalhando em múltiplos projetos, certifique-se de ter distinção entre docs que tem as mesmas regras para TODOS os GESTORES vs DOCS que são exclusivos para um ou outro GESTOR ou especialmente para PROJETOS ESPECÍFICOS. 
6. Tarefas exclusivas de cada projeto devem estar nas tasks do projeto ou provavelmente devem estar nas pastas exclusivas do projeto nas docs do Gestor, pois então isso, para diferenciar dentre as tasks específicas de um projeto de algo que é pra TODOS os gestores saberem ou cumprirem.
